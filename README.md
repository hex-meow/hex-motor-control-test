# hexfellow CANopen Motor Control Demo

Two minimal C demos that initialize and drive **hexfellow** motors over
CAN-FD using the CANopen (CiA301 + CiA402) protocol with vendor
extensions for 64-byte PDOs.

- `demo_mit` — spins every motor at a constant velocity using **MIT
  mode** (`6060h = 5`).
- `demo_velocity` — spins every motor at a constant velocity using
  **profile-velocity mode** (`6060h = 3`) with a per-frame `6072h`
  torque limit.

This repo is intentionally a **demo**, not a library. It contains the
bare minimum to bring the motors from cold-boot all the way to a
constantly moving steady state and to print telemetry; if anything
goes wrong during init, the program prints a message and exits.

See [`project-structure.md`](project-structure.md) for a per-file tour
of the codebase.

## Why no CANopenNode dependency?

The well-known [CANopenNode](https://github.com/CANopenNode/CANopenNode)
stack would have been the natural choice for the SDO traffic during
initialization. We deliberately do **not** use it, for two reasons:

1. **No 64-byte CAN-FD PDO support.** The hexfellow firmware uses
   vendor-extended 64-byte FD PDOs to pack one-to-many control data
   for up to 8 motors into a single frame. CANopenNode v1.3 (the most
   recent stable line at the time of writing) does not natively handle
   FD PDOs of that size, so the runtime path needed to be custom
   regardless.
2. **Disproportionate footprint for SDO-only use.** Pulling in
   CANopenNode purely to run a handful of expedited SDO transfers
   during init would dwarf the rest of this demo, drag in object
   dictionary tooling, and obscure the actual on-wire behavior we're
   trying to teach.

Instead, [`src/hexfellow_sdo.c`](src/hexfellow_sdo.c) implements a
minimal expedited SDO master in ~200 lines of C — enough for every
object the initialization sequence touches (all transfers are ≤ 4
bytes). The control-loop path then talks straight to a SocketCAN-FD
socket. The whole binary depends only on `libc`, `libpthread`, and
`libm`.

If your application needs full CiA301 services (segmented/block SDO,
remote NMT, EMCY, dynamic OD, ...), use a real CANopen stack — this
demo is not that.

## Hard-coded presets

The demos make a number of fixed assumptions to keep the code small
and readable. If your setup deviates, edit
[`src/hexfellow_common.h`](src/hexfellow_common.h).

| Item | Value |
| --- | --- |
| CANopen IDs of motors | **must start at 1 and be sequential** (1, 2, … N) |
| Maximum motor count `N` | **8** (`8 motors × 8 bytes/motor = 64 byte CAN-FD frame`) |
| Master node ID | **`0x10`** (heartbeat producer at COB-ID `0x710`) |
| Shared RPDO COB-ID | **`0x190`** (= master TPDO1 default) |
| Required firmware version | **exactly `8`** (validated via `1018h-03`) |
| Expected factory UID | **`0x4859444C`** (validated via `1018h-01`) |
| Master heartbeat period | **50 ms** |
| Motor consumer-heartbeat timeout | **250 ms** (motors monitor master at `0x710`) |
| TPDO1 (`pos f32 / ts u32 / torque i16 / err u16`, 12 B) | event timer 1 ms, inhibit 0.5 ms |
| TPDO2 (`status / drv-T / mtr-T / ctrl / err`, 12 B) | event timer 20 ms, inhibit 19 ms |
| RPDO1 transmission type | 255 (event-driven) |
| Short-circuit braking on disable (`2040h`) | enabled |
| RPDO send cadence | **2 ms** (`HEXFELLOW_RPDO_PERIOD_MS`) |
| Heartbeat warm-up window | **100 ms** (zero-target RPDO before rotation command) |

## Startup contract (heartbeat / rotation ordering)

The motor firmware has a strict ordering requirement that the demo
must respect:

1. **No master heartbeats are sent during SDO initialization.** The
   firmware's consumer-heartbeat watchdog (object `1016h-01`, 250 ms)
   is only *armed* once the motor receives the first heartbeat from
   the master. Sending heartbeats too early — for example while the
   next motor is still being SDO-configured — would arm the watchdog
   and then miss the next heartbeat deadline, tripping motor fault
   `0x8130` "Heartbeat error".
2. **Heartbeat-first ordering inside the control thread.**
   `hexfellow_ctrl_start` spawns a single thread that runs a tight
   `HB-if-due → RPDO → drain → sleep` loop. The first iteration's
   "HB due" check fires immediately (`last_hb_ms = 0`), so the very
   first frame the thread emits is a heartbeat on cob `0x710` — before
   any RPDO. After that, the application waits a 100 ms warm-up
   window (during which RPDOs carry a zero target and command no
   motion) and then writes the real target.
3. **Heartbeats and RPDOs share one thread, by design.** This is
   intentional coupling: if the RPDO `write()` path ever wedges, the
   heartbeat stops too, the motor's 250 ms consumer-heartbeat watchdog
   trips, and the failure is *visible* — the motor stops cleanly
   rather than continuing to spin on a stale target. The thread
   carries the heartbeat at 50 ms cadence and the shared RPDO at 2 ms
   cadence.
4. **CAN-FD frames are always sent with `CANFD_BRS`.** Some CAN-FD
   controllers refuse to actually transmit FD frames whose data phase
   would run at the arbitration bitrate; without BRS the first RPDO
   wedges in the TX queue and blocks every subsequent send (including
   heartbeats).
5. **TPDO drain is fully non-blocking (`MSG_DONTWAIT`).** Motors emit
   TPDO1 every 1 ms; a blocking `read()` with `SO_RCVTIMEO = 1 ms` is
   ambushed by the next arriving frame and never returns, starving
   the RPDO send path even though heartbeats keep flowing. `drain_rx`
   pulls everything currently in the kernel RX queue and returns
   immediately the queue is empty.

If you see motors halting almost immediately after `demo_*` reports
"applying targets", check that the warm-up window is large enough for
your bus latency and that no other producer on the bus is delaying
the first heartbeat.

## Shutdown contract (no graceful disable)

There is intentionally **no graceful disable** in either demo:

- `SIGINT` / `SIGTERM` call `_exit(0)` directly from the signal
  handler. The kernel tears down the process immediately; no SDO
  writes, no NMT pre-operational broadcast, no thread join.
- When heartbeats stop arriving, every motor's own consumer-heartbeat
  watchdog trips after 250 ms and the firmware disables the drive
  with short-circuit braking (because we set `2040h = 1` during
  init).

So pressing `Ctrl+C` produces:

```
demo exits immediately  →  ~250 ms later motors stop  →  bus is idle
```

## Prerequisites: bring the CAN bus up

The demos do **not** configure SocketCAN themselves — they assume the
interface is already UP and configured for CAN-FD. The recommended
configuration is:

```bash
# Arbitration: 1 Mbps @ sample-point 0.8
# Data:        5 Mbps @ sample-point 0.75
sudo ip link set can0 type can bitrate 1000000 sample-point 0.8 \
        dbitrate 5000000 sample-point 0.75 sjw 5 dsjw 3 fd on
sudo ip link set up can0
```

If your USB-CAN adapter does not support those exact sample points,
use a hardware CAN-FD-capable SoC (e.g. RK3576) instead. Long frames
will fail silently if the timing is wrong.

If anything is misconfigured, the demos will fail to open the socket
with a descriptive error and exit.

## Build

### Native (host)

```bash
make
```

Outputs land in `build/demo_mit` and `build/demo_velocity`.

### Cross compile

The Makefile honors the standard environment variables (`CC`,
`CFLAGS_EXTRA`, `LDFLAGS_EXTRA`) so any cross toolchain works. A
typical Buildroot toolchain build for a Cortex-A53 target (e.g.
RK3576) looks like:

```bash
# adjust to your absolute Buildroot path
export BR=/path/to/buildroot

env CC=$BR/output/host/bin/aarch64-linux-gcc \
    CFLAGS_EXTRA='-mcpu=cortex-a53' \
    make

scp build/demo_mit build/demo_velocity root@<board_ip>:
```

Alternatively, with a Debian-style cross compiler:

```bash
env CC=aarch64-linux-gnu-gcc make
```

Each toolchain produces a self-contained binary that depends only on
`libpthread`, `libm` and `libc`. The Makefile also accepts
`BUILD_DIR=...` if you want output somewhere other than `./build`.

### Clean

```bash
make clean
```

## Run

Both demos accept the same first two positional arguments and a few
optional knobs. A `--verbose` (or `-v`) flag can appear anywhere on
the command line.

```text
demo_mit       [--verbose|-v] <iface> <motor_count> [target_rev_per_s=0.5] [kd=2.0] [torque_permille=800]
demo_velocity  [--verbose|-v] <iface> <motor_count> [target_rev_per_s=0.5] [torque_permille=200]
```

Examples — assuming 4 motors with CANopen IDs `0x01..0x04` on `can0`:

```bash
# MIT mode, 0.5 rev/s, kd=2.0, max torque 80% of peak
./build/demo_mit can0 4 0.5

# Profile-velocity mode, 1.0 rev/s, max torque 20% of peak
./build/demo_velocity can0 4 1.0 200

# Same but with verbose printf-debug logging on stderr
./build/demo_mit --verbose can0 4 0.5
```

### Verbose logging

When `--verbose` is set, the control thread emits short `[v] ...`
lines on stderr:

```text
[v] ctrl thread started; HB period=50 ms, RPDO period=2 ms
[v] 12345ms HB sent (0x710)
[v] 12347ms drain: T1=2 T2=0 other=0
[v] 12445ms RPDO sent (count=50)     # rate-limited to ~10/sec
[v] 12500ms ctrl loop fell behind by 8 ms     # only if scheduling is bad
```

RPDO sends are emitted at 500 Hz so their verbose log is intentionally
rate-limited to one line every ~50 sends (~100 ms apart) — that's
still enough to spot gaps. Heartbeats and TPDO drains are logged
unfiltered. Pipe stderr through `grep` / `head` if you want to focus
on a single event type.

You should see initialization logs for each motor:

```text
[hexfellow] initializing motor #0 (CANopen id 1)
[hexfellow] motor #0 id=1 OK (fw=8 serial=0x12345678 peak=15000 mNm)
...
[demo_mit] heartbeat warm-up (100 ms) before applying targets
```

followed by once-per-second telemetry per motor (position, multi-turn
counter, torque, status word, error code, driver and motor
temperatures).

Press `Ctrl+C` to immediately terminate the process; the motors stop
on their own ~250 ms later (heartbeat watchdog timeout).

## Architecture overview

```
                      can0 (CAN-FD UP)
                            │
   ┌────────────────────────┴────────────────────────┐
   │                                                 │
classic 8 B socket                              CAN-FD socket
(only used for SDO)                       (NMT, heartbeat 0x710,
                                          RPDO 0x190 64 B FD,
                                          TPDO1/TPDO2 RX 12 B FD)
   │                                                 │
hexfellow_sdo.c                              hexfellow_canfd.c
   │                                                 │
   ▼                                                 ▼
hexfellow_motor_init.c       ────────►       hexfellow_motor_ctrl.c
(per-motor SDO config:                      (single 2 ms control thread:
 UID/version/peak-torque,                    HB-if-due (50 ms cadence),
 PDO mapping & one-to-many                   pack RPDO from latest targets,
 RPDO COB-ID rewrite,                        drain incoming TPDO1/TPDO2,
 CiA402 enable, NMT operational)             nanosleep to next 2 ms tick)
```

Initialization is performed up-front, sequentially, motor by motor.
Once all motors are in *Operational* state the SDO socket is left idle
and the high-rate path is exclusively the 2 ms RPDO/TPDO loop on the
CAN-FD socket. The same loop also emits the 50 ms master heartbeat.

## Error policy

This is a demo — there is **no** error recovery. Anything that goes
wrong during initialization (SDO timeout, abort, factory UID mismatch,
firmware version not equal to 8, …) prints an explanatory message to
`stderr` and calls `exit(EXIT_FAILURE)`. At runtime any unexpected
condition (failed send on the CAN-FD socket, for example) is also
fatal. The CAN bus is left unconfigured by us; if you need a clean
state, power-cycle the motors.
